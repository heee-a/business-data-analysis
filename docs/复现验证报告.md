## 一、验证目的

证明「他人克隆仓库 → 执行一条命令 → 得到与仓库中完全一致的产物」这一主张成立，
而非仅凭随机种子字段自证。

## 二、验证方法

| 步骤 | 操作 | 说明 |
| :--: | --- | --- |
| 1 | `git archive HEAD \| tar -x -C <干净目录>` | 导出**已提交内容**（等同全新克隆，排除本地未提交文件干扰） |
| 2 | `python run_all.py` | 在干净目录中完整执行 STEP 01–10 |
| 3 | 逐文件比对 | 与主开发目录的 `outputs/figures/`、`outputs/tables/`、`outputs/html/`、`docs/` 做**字节级**比对 |

设计要点：不使用开发目录直接重跑（会掩盖「仓库缺文件」类问题），
而是从已提交快照出发，模拟他人克隆后的真实处境。

比对口径说明：JSON 结果表中的 `started_at / finished_at` 等运行时间戳字段
属运行元数据而非分析内容，比对前统一剔除后再哈希；
其余产物（图片、CSV、组件 HTML、docx、xlsx）均为原始字节比对。

## 五、验证中发现并已修复的五处非确定性

复现实验的价值正在于暴露这类问题 —— 二者在单次运行中都不会报错，
但会导致「每次跑出来的图和表都不一样」。
前四处发现于 2026-10-20 的首轮验证，第五处发现于 2026-10-21 的复验。

### 5.1 词云图布局随机（`scripts/04_visuals.py`）

- **现象**：`fig24_wordcloud_products.png` 两次运行 MD5 不同。
- **根因**：`wordcloud.WordCloud` 内部使用随机布局算法，
  未传入 `random_state` 时每次调用产生不同的词位与旋转角度。
- **修复**：传入 `random_state=cfg.RANDOM_SEED`（2026）。
- **验证**：修复后连续两次运行，37 张图 MD5 全部一致。

### 5.2 Apriori 规则排序不稳定（`scripts/03_analysis.py`）

- **现象**：`03_apriori_rules*.csv/json` 中同 `lift` 的多条规则次序在跨运行间变化。
- **根因**：`mlxtend` 的 `frozenset` 迭代顺序受集合哈希影响，
  仅按 `lift` 单键排序时，并列规则的相对次序不稳定（Python 的 `sort_values` 稳定，
  但输入顺序本身不稳定）。
- **修复**：排序改为全序 tie-breaker ——
  `lift → confidence → support → antecedents → consequents`，
  末两级为字符串比较，不依赖任何哈希次序。
- **验证**：连续两次运行，三个 Apriori 结果文件 MD5 完全一致。

> 这两处修复同时消除了「图表/结果表与仓库不一致」的隐患：
> 在此之前，仓库中提交的 JSON 与重新生成的产物确实存在可观测差异。

### 5.3 OOXML 容器打包时间戳（`scripts/utils/io_utils.py`）

- **现象**：`docs/*.docx` 连续两次运行 MD5 不同，尽管正文内容一字未改。
- **根因**：`.docx` 本质是 ZIP 容器，`python-docx` 落盘时每个条目的
  `date_time` 取自系统当前时刻；内容相同而二进制不同，
  既让 MD5 比对失败（看起来像「不可复现」），也会让 Git 记录纯噪声的大文件 diff。
- **修复**：新增 `iou.stabilize_zip_package()`，在保存后重写容器——
  条目顺序、压缩方式、权限位与外部属性原样保留，仅把时间戳固定为常量；
  目标文件若正被 Word/Excel 占用则降级为「跳过并告警」，不阻断流水线。
  这与本项目 `gz_archive()` 里 `mtime=0` 的做法同源，
  共同服务于「内容不变则字节不变」。
- **验证**：连续两次运行 docx MD5 完全一致；并由本机 Word 实际打开验证可用、成功导出 PDF。

### 5.4 Excel 工作簿元数据时间戳（`scripts/09_excel_summary.py`）

- **现象**：`00_关键结果汇总.xlsx` 两次运行 MD5 不同；条目级定位显示差异只出自 `docProps/core.xml`。
- **根因**：`openpyxl` 在 `save()` 时会把 `dcterms:modified` 覆写为当前时刻——
  即使在保存前显式设置 `workbook.properties.modified` 也会被盖掉。
- **修复**：两步处理。① 在写入前固定 `creator / lastModifiedBy / title / created`；
  ② 由 `stabilize_zip_package()` 对 `docProps/core.xml` 再做一次时间字段正则规范化，
  覆盖 save 时刻被改写的值。
- **验证**：连续两次运行 xlsx MD5 完全一致，且 ZIP 条目级校验（`testzip()`）无错误。

### 5.5 Pyecharts 组件容器 ID 随机（`scripts/05_dashboard.py`）

- **现象**：2026-10-21 复验时，22 个大屏组件 HTML **全部**字节不一致，
  但逐字节 diff 显示图表配置（series、option、配色）完全相同。
- **根因**：`render_embed()` 每次调用为图表容器生成一个随机 UUID 作为 `div id`
  （如 `b13b79490fde4d2b807a1244d06c4218`），同一配置两次渲染的字节自然不同。
  该 ID 同时被组装进 `dashboard_dark.html` 与离线包，影响面覆盖全部大屏产物。
- **修复**：在 `build_components()` 的 `add()` 中统一
  `chart.chart_id = <组件键名>`（如 `tab1_trend`），
  容器 ID 变为语义化固定值，组件 HTML 与组装后的大屏均跨运行确定。
- **验证**：复验后 22 个组件 HTML 字节级一致；本机浏览器实拍截图确认图表渲染正常。

## 六、复现步骤（他人可照做）

```bash
git clone git@github.com:heee-a/business-data-analysis.git
cd business-data-analysis
pip install -r requirements.txt
python run_all.py            # STEP 01–10，约 7 分钟（STEP 01 需联网下载 45 MB 源数据）
```

`run_all.py` 会依次执行全部 10 个阶段；其中 STEP 07/08/09/10 标记为「可容忍失败」
（依赖外部资源：JS 库 CDN、桌面归档目录、本机 Chrome），缺失时自动告警并继续，
不阻断主流程。在完整环境（联网 + Chrome）下约 7–10 分钟跑完。

可选参数：`python run_all.py --list` 查看阶段清单，
`--skip 1 2` 跳过数据获取与清洗（复用已有中间结果），
`--only 4 5` 仅重跑图表与大屏。
