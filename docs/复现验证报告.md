## 一、验证目的

证明「他人克隆仓库 → 执行一条命令 → 得到与仓库中完全一致的产物」这一主张成立，
而非仅凭随机种子字段自证。

## 二、验证方法

| 步骤 | 操作 | 说明 |
| :--: | --- | --- |
| 1 | `git archive HEAD \| tar -x -C <干净目录>` | 导出**已提交内容**（等同全新克隆，排除本地未提交文件干扰） |
| 2 | `python run_all.py` | 在干净目录中完整执行 STEP 01–10 |
| 3 | 逐文件比对 | 与主开发目录的 `outputs/figures/`、`outputs/tables/` 做**字节级**比对 |

设计要点：不使用开发目录直接重跑（会掩盖「仓库缺文件」类问题），
而是从已提交快照出发，模拟他人克隆后的真实处境。

## 五、验证中发现并已修复的两处非确定性

复现实验的价值正在于暴露这类问题 —— 二者在单次运行中都不会报错，
但会导致「每次跑出来的图和表都不一样」。

### 5.1 词云图布局随机（`scripts/04_visuals.py`）

- **现象**：`fig24_wordcloud_products.png` 两次运行 MD5 不同。
- **根因**：`wordcloud.WordCloud` 内部使用随机布局算法，
  未传入 `random_state` 时每次调用产生不同的词位与旋转角度。
- **修复**：传入 `random_state=cfg.RANDOM_SEED`（2026）。
- **验证**：修复后连续两次运行，35 张图 MD5 全部一致。

### 5.2 Apriori 规则排序不稳定（`scripts/03_analysis.py`）

- **现象**：`03_apriori_rules*.csv/json` 中同 `lift` 的多条规则次序在跨运行间变化。
- **根因**：`mlxtend` 的 `frozenset` 迭代顺序受集合哈希影响，
  仅按 `lift` 单键排序时，并列规则的相对次序不稳定（Python 的 `sort_values` 稳定，
  但输入顺序本身不稳定）。
- **修复**：排序改为全序 tie-breaker ——
  `lift → confidence → support → antecedents → consequents`，
  末两级为字符串比较，不依赖任何哈希次序。
- **验证**：连续两次运行，三个 Apriori 结果文件 MD5 完全一致。

> 这两处修复同时消除了「图表/结果表与仓库不一致」的隐患：
> 在此之前，仓库中提交的 JSON 与重新生成的产物确实存在可观测差异。

## 六、复现步骤（他人可照做）

```bash
git clone git@github.com:heee-a/business-data-analysis.git
cd business-data-analysis
pip install -r requirements.txt
python run_all.py            # STEP 01–09，约 7 分钟（STEP 01 需联网下载 45 MB 源数据）
python scripts/10_dashboard_screenshots.py   # 可选：大屏演示截图，需本机 Chrome
```

可选参数：`python run_all.py --list` 查看阶段清单，
`--skip 1 2` 跳过数据获取与清洗（复用已有中间结果），
`--only 4 5` 仅重跑图表与大屏。

## 七、已知的非字节级一致项（属预期，非缺陷）

| 项 | 原因 |
| --- | --- |
| `outputs/tables/00_关键结果汇总.xlsx` | xlsx 为 zip 容器，含文件时间戳，字节不稳定；内容一致 |

| 大屏演示截图 PNG | 依赖本机 Chrome 版本与字体渲染，像素可能有细微差异 |
| 各脚本日志中的时间戳 | 运行时生成，非产物内容 |
